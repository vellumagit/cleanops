# Job-state cutover — Saturday 2026-11-14

Slice 8 of `finish-plan-2026-10-28.md`. One setting moves the job status
from shadow mode (the rules compute, the old writers save) to write mode (the
rules save). Decided 2026-11-09.

## What changes

- `JOB_STATE_WRITE=1` in Vercel → Production. `syncJob` (src/lib/job-sync.ts)
  stores the computed status after every tap, click and heartbeat, logs a
  `status_change` audit row, and drafts the invoice when a job completes.
- The 2 AM sweep (`autoCompletePastBookings`, src/lib/automations/job-lifecycle.ts)
  no longer writes `completed` itself in write mode; it asks the rules about
  each due job. The two used to race: the sweep set completed and drafted the
  invoice, then its own recompute reverted the job (docs/job-lifecycle-map.md §4).
- That sweep change is **mode-gated**, so the code ships early and runs
  unchanged in shadow mode until the flag is set. Saturday is the flag and a
  redeploy, nothing else.
- Visible difference for the office: a staffed job nobody tapped closes at
  **window end + the org's grace** on the half-hourly heartbeat, during the
  day, instead of at 2 AM. The sweep's watchdog emails (never staffed, still
  on the clock, stale pending) are unchanged.

## Rolling back

Remove `JOB_STATE_WRITE` in Vercel, then redeploy (Deployments → latest →
Redeploy, or another empty commit). The code is mode-gated, so shadow mode
comes back whole: the sweep writes again, the rules only log.

`vercel rollback` to a pre-flip deployment also works and is faster, but
remove the variable too, or the next push flips again.

Nothing in the data needs undoing: write mode stores the same statuses
shadow mode has been checking against for weeks, and every write is guarded
on the status it read, so a human's change always wins.
