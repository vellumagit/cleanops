# Cron + notification-sender map — cleanops, 2026-10-28

Read-only inventory. Every claim below was checked by reading the route and its helper, not by grep proximity. Line numbers are as of HEAD `b9075e4`. Nothing was edited.

Conventions used in the tables:

- **ERR→[]** — the query's `error` is never looked at; `data ?? []` (or `!data → return`) makes a failed read look like "no rows".
- **ERR→throw** — the error is checked and thrown/returned 500.
- **ERR→log** — logged, then continues with empty data (same effect as ERR→[] but visible in logs).
- **mark-before / mark-after** — whether the dedupe stamp is written before or after the send.
- **cliff** — an unchunked `.in(col, ids)`; PostgREST URL limit ≈390 UUIDs (`src/lib/supabase/chunked-in.ts` documents it; `selectInChunks` uses 150).
- **clamp** — PostgREST's 1000-row response cap; a `.limit()` above 1000 is silently 1000.
- Unless stated, every cron is protected by `requireCronAuth` (fails closed when `CRON_SECRET` is unset) and iterates **all orgs** with no org filter other than what's listed.

### The 2 AM sweep vs `syncLiveJobs`: can both close the same job?

- **Today (shadow mode, `JOB_STATE_WRITE` unset — nothing in the repo or env files sets it; `docs/finish-plan-2026-10-28.md` row 8 schedules it for Sat Nov 7):** no. Only `autoCompletePastBookings` writes `bookings.status`. `syncLiveJobs` writes an `audit_log` `state_check` row where the computed state disagrees, deduped against the previous row. The sweep's own trailing `syncJob(b,"nightly_sweep")` (automations.ts:7450) records the disagreement the comment there predicts.
- **After cutover (write mode):** yes, and the order matters:
  1. The sweep's criterion is `scheduled_at < now − H` (H = `booking_auto_complete_hours`, measured from the job's **start**). The heartbeat's is `now ≥ windowEnd + H` (`job-state.ts:262–266`, measured from the **end** of the crew's shared window). The sweep therefore fires earlier by `teamMinutes`.
  2. In that gap, the sweep sets `completed` (7409, no status guard), calls `autoInvoiceOnJobComplete` (invoice drafted; auto-send scheduled), then calls `syncJob(b,"nightly_sweep")`. In write mode `syncJob` recomputes `confirmed` (window end + grace not yet reached), and its guarded update `.eq("status","completed")` succeeds → the job is **reverted to confirmed with a drafted (and possibly scheduled-to-send) invoice**. The next heartbeat at `windowEnd+H` completes it again; `autoInvoiceOnJobComplete` then finds the existing invoice (dedupe at 320) and does not draft a second.
  3. Simultaneous completion at 02:00 (sweep and heartbeat in the same minute): the heartbeat's status write is guarded on the status it read; the sweep's is not but is idempotent. Two concurrent `autoInvoiceOnJobComplete` calls can both pass the existing-invoice read, but the partial unique index `invoices(booking_id) where voided_at is null` (migration `20260821010000`) makes the second insert fail — so **no double invoice**, just a logged insert error.
  4. The plan deletes "the old status-writing paths" only after the Monday-morning check, so the sweep on Nov 8 and Nov 9 at 02:00 runs with both paths live.
